# 06 — Open docs PR and post readiness

Trigger: explicit `open-pr` option after 05. Inputs DocsRepoId, DocsBranch, doc/release, md/docx/manifest, changedSectionIds, gapCount, requiredReviewerIds, Readiness. Outputs PR ID/URL/status and draft branch; no source-system writes.

1. Guard repository ID against the configured docs-repo allowlist. Source reader identity has no write permission; docs writer has only repository branch/commit/PR/status permission. Never use work-item/test modification actions, even for proposals. Reject any dynamic URL targeting the device repo.
2. GET docs repo refs and current main objectId, tags and approved document baseline. Branch `dhf/<doc>/<release>/<UTC requestId>` must be new. Use ADO HTTP POST `<project>/_apis/git/repositories/<DocsRepoId>/pushes?api-version=7.1` with refUpdates name new branch and oldObjectId all zeroes, commit parent main objectId, and changes adding/updating only document files. Text contentType rawtext; DOCX content base64encoded. Supply actual bytes, not Markdown disguised as DOCX. If connector payload limitations prevent a bundle, stage verified files in SharePoint and use the approved docs-push function; no successful PR claim until Git contents are verified.
3. GET the pushed branch items and confirm content hashes match the intended files. Concurrent main changes do not permit silent overwrite; ref/parent conflicts become reviewable retries of branch creation, never a forced push to main.
4. POST `<project>/_apis/git/repositories/<DocsRepoId>/pullrequests?api-version=7.1`, JSON sourceRefName, targetRefName, title, description (changed sections, claim counts, deterministic gaps, human/eQMS review outstanding), reviewers with isRequired=true. All inputs are deterministic run metadata. Do not auto-complete or merge.
5. Persist PR URL in manifest and push the updated manifest to the same draft branch, then POST `.../pullrequests/<id>/statuses?api-version=7.1` with context name DHF review readiness, genre dhf, state succeeded only if ready, else failed; description uses counts, not provider output. Required-reviewer checks and eQMS signoff remain human.
6. `check` fetches current PR branch, reads actual edited Markdown, revalidates dispositions and manual authoring, re-renders DOCX, refreshes checksum and status. Deleting a suggestion label does not resolve its claim. Tag `<doc>-vN` is created only after a human-completed merge and a successful readiness/content check; numeric versions increment deterministically.
7. Return PR URL to the job-status topic. Notifications use only the explicitly configured/authorized channel; do not send arbitrary email or messages. Test/demo merging belongs to separate synthetic test tooling, never this flow.

Git Pushes and PR REST payload examples in `contracts/docs_push.json` are templates; replace byte hashes/parent commit IDs with validated run values.
