# 07 — Change impact, watch and selective regeneration

Trigger: ADO **When a work item is updated**, plus a recurrence poll (default 60 seconds). Inputs organization/project, last complete snapshot, latest approved baselines/current draft manifests, regeneration/open-PR preferences. Output impact Markdown/JSON and optionally a docs-only redline PR.

1. Queue one ingest per organization; complete 01–02 before impact. Read full native source revisions and hashes plus confirmed links. The connector update trigger can miss added/deleted links, so the recurrence path is required, not merely a backup. Deduplicate events by organization/nativeID/revision; no event payload becomes an instruction. [Connector trigger limitation](https://learn.microsoft.com/en-us/connectors/visualstudioteamservices/).
2. Diff snapshot membership and revision/hash, also confirmed-edge changes attributed to their source. Document baseline means its recorded source snapshot; `since` can select a stored ingest snapshot or latest at/before a UTC timestamp. Include additions/removals as separate cause IDs.
3. Direct stale section = intersection(changed IDs, cited_revisions keys). Added results or changed query membership/facts can stale sections without an old citation naming them. Re-run deterministic queries and compare authoritative facts (exclude source_numbers validation context). Name changed facts IDs or the confirmed dependency cause in the report. Never mark a numerical-context-only change as a content change.
4. Possible impact = section cites a confirmed one-hop neighbor of a changed artifact. Keep status possibly_affected, source/via/reason. Collapse sibling unit subsections into optional unit review groups in Markdown. JSON keeps individual IDs for evaluation; these flags do not block readiness or cause automatic regeneration.
5. Persist evidenceStatus stale on directly stale sections; readiness now fails until refreshed. Report per-document stale/possible counts at top. New/removed repeated entities are explicit structural changes. Keep current section Markdown separate from original generated metadata so owner edits survive.
6. If regenerate requested, call 04 only for stale/new sections. Preserve all other actual edited section bytes; reassemble with new snapshot and manifest. Compute DOCX diff against the approved current baseline and open a docs-only PR listing impacted section IDs. Do not create a new baseline or approve any new suggestion automatically.
7. Save the initial impact report before regeneration for evaluation against frozen change_1 expectations. Do not score an empty post-regeneration report as perfect detection. If a follow-up ingest is unchanged, emit no repeat PR. For continuous watch, track cancellations and terminate cleanly; for demo use finite cycles.
8. Test the trigger and polling paths separately. If webhook installation is disallowed, leave the recurrence flow enabled and document the limitation. Expected source changes: SRS-021 and UNIT-sensor_pressure; additions PR-8/RUN-3/RES-3-021. Exact section/status/cause records are in the frozen scenario fixture.
